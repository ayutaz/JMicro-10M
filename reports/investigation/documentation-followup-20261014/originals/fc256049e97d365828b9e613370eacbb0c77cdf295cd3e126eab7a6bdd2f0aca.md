# Chatの課題を解決するための段階計画

作成: 2026-10-12 JST。ユーザーの「これらの問題に対する課題の解決方法とその計画を立ててください」に対応する。[調査130](130_chat_failure_improvement_investigation.md)を、対策・比較・成果物・進行/停止条件へ具体化した。**今回は計画作成のみ。新しい教材、実行config、runner、GPU推論・学習は作成/実行していない。** 以下の数値は事前提案で、測定済みの改善効果や実行許可ではない。

## 1. 目標と固定する条件

流暢に止まるだけでなく、短い日本語の質問に関連した回答を返し、訂正・否定・複数条件を保持するChat候補を、10Mのまま作る。最初の一巡は教材改善の比較と結果報告までで止める。日本語Baseの品質目標と未採用状態は維持する。

| 項目 | 固定する内容 |
|---|---|
| 学生モデル | 現10,001,152 parameters。元予算9.5M–10.1M、大型化なし |
| 構成・Tokenizer | native model.py、13層/hidden256/context1024、既存4k Tokenizer |
| 比較の親 | 元WebUI10B `checkpoint-00305176.pt`、SHA256 `410f975d848938627aafb4fa1d5483bf45fadbb7f9c05ed7d1c8f9d45c368290` |
| 初期化 | 各条件が同じ親の重みから開始。fresh AdamW、学習seed42、全parameter更新 |
| 基本最適化 | LR最大1e-4、weight_decay0.01、betas(0.9,0.95)、clip1.0、BF16/math、compile=false |
| 教師 | 現Assistant本文+EOTのみ。User/system/role/PAD/過去Assistantのlabelは−100 |
| 生成 | greedy、max_new_tokens64、EOT7/EOS3。既存特殊token抑制と無抑制control |
| 保全 | 親、旧3周SFT、raw、原採点、Tokenizer、Phase0–3、閉鎖済み比較を保持 |
| 後続範囲 | 量子化、deployment、公開/push、有料API、大型モデル比較へ自動移行しない |

旧3周候補へ教材を継ぎ足すと学習履歴が交絡するため、第一比較は同じ元親から開始する。旧採用済みBase gateはそのまま残し、未採用親を使う追加診断は専用入口で明示する。既存[計画128](128_chat_first_sft_plan.md)の結果は[129](129_chat_first_sft_execution.md)で閉鎖済みであり、再起動しない。

## 3. 最初の実験を2条件に絞る

| 条件 | 教材 | 意図 |
|---|---|---|
| C0 対照 | 既存RealPersonaChat TRAIN、原本文/役割の現版 | 共通の教師量契約における雑談SFTの基準 |
| C1 改善案 | 日常会話を残し、役割・直接回答・訂正・否定・文脈を明示した別版教材 | 教材recipe全体の改善効果 |

両方に同じ新しい教師量契約を適用する。C0は旧runの再開ではなく、新run ID/新contractの対照である。2026-10-10の3周結果は履歴参照で、同条件対照に代用しない。複数能力の教材をまとめて変えるため、比較が示せるのはrecipe全体の効果であり、訂正例だけ等の独立した寄与ではない。

### 教材の構成案

割合は**実際に消費するAssistant本文+EOT教師tokensの割合**で、会話件数比ではない。以下の1recipeを提案し、比率の総当たりはしない。

| 教材分類 | 教師量比の案 | 教える内容 |
|---|---:|---|
| 日常・挨拶・感情・自然な後続会話 | 30% | 文脈に合う相づちと会話の継続 |
| 明確な質問への直接回答 | 20% | 問いに答えてから補足する |
| 訂正 | 15% | 最新の訂正を優先する |
| 否定・複数制約 | 15% | 条件を同時に守り、否定の有無で答えを変える |
| 複数turnの参照・要約 | 10% | 2–4turnで対象と条件を保持する |
| 曖昧さ・必要な聞き返し | 5% | 不足情報がある時だけ具体的に確認する |
| 話者・役割の区別 | 5% | Userの属性とAssistantの提案等を区別する |
| 合計 | 100% | 元の幅広い短い日本語Chat目標を維持 |

数字・名前・記号・表記揺れは上記を横断して含める。評価を特定のテンプレートや小さな語彙へ狭めない。新規の小さな構造化会話と、根拠を確認して選別/別版化した自然な会話を併用する。元RealPersonaChatを使う場合は帰属とsharealike bucketを保持し、派生版の元IDと編集理由を記録する。元本文や旧splitを上書きしない。

1周で有効教師65万tokens以上を準備する案とし、約1.9Mの比較で3周を超えて同じtargetを繰り返さない。これは教師出現量であり、全て独立した新情報という意味ではない。件数は実Tokenize後に決める。各能力は複数の独立した文型/自然会話由来のfamilyを持ち、単一familyが一分類の教師量の5%を超えない設計にする。厳密重複と近い派生例は一つのfamilyへまとめる。

### 作成・品質gate

1. TRAIN設計と評価の能力分類を先に記録し、教材作成側は新DEVの具体的な問題・正答を読まずに作成する。旧DEVの質問・正答・失敗出力をTRAINへ移さない。
2. 元会話/生成template familyをsplitの単位にする。未使用DEVは文型・対象値の組合せ・自然文を分離し、単なる値違いの問題だけにしない。新しい限定教材に対する重複確認は行うが、一般Web全corpusの再走査はしない。
3. 応答は本文の情報から成立し、最新の訂正と全制約を満たすこと。条件が不足する時だけ聞き返す。「分かりません」「そうですね」等へ一律に逃げる版を作らない。欠けたpersonaを創作せず、モデル本人の経歴にしない。
4. schema、UTF-8、話者交互、TRAIN分離、完全EOT、mask、根拠slotは全件機械確認する。意味の正しさはキーワード出現だけで認証しない。制御生成の規則と正解条件を突合し、自然文への編集後も再確認する。
5. 各分類40件、合計280targetを事前seedで抽出し、文法・役割・根拠・条件を内容レビューする。誤りが見つかれば同じ生成元familyを点検・修正/除外し、別の固定sampleで再確認する。280件の確認を全TRAINの人間認証とは呼ばない。
6. target長は2–65（EOT込み）の共通範囲。EOT割合と長さhistogramをC0/C1で記録する。EOT割合差1 percentage point以内、4区間（2–8/9–16/17–32/33–65）の長さ分布のtotal variation distance0.10以内を設計目標とする。短くするために必要条件を落とさない。満たせなければ教材案を再設計し、差を隠して学習を開始しない。

自然文全体の意味を完全自動認証したとは扱わない。人間の独立した教材レビューが未確保なら、その未完了を記録する。最終品質確認の人間blind評価とは別である。

## 4. 教師量・schedule・保存再開の共通契約

現runnerは直列series予算と更新数を使用し、最終教師/応答数を旧3周専用の値でassertする。[現runner](../scripts/run_chat_first_sft.py)。そのまま新教材へ流用せず、**新しい専用contract/runnerを再開後に実装する必要がある。** 今回はコードを変更しない。

| 項目 | 事前提案 |
|---|---|
| 本比較の教師budget B | 各条件1,899,555 Assistant本文+EOT tokens |
| 終端 | 完全targetを保ち、完了更新で停止。最終目標量を超える量は最大64教師tokens |
| 実効batch | 通常更新は教師512を下限として完全targetを積み、512–576教師/更新。最終更新のみ残budgetを下限にする |
| 物理microbatch | 既存実測32を上限候補とし、必要に応じ複数microbatch。初回は現1024固定paddingのまま |
| loss | 全microbatchのCE sum / その更新の実教師数。microbatch平均を単純平均しない |
| LR進行 | 更新前の完了教師Tと当該更新の実教師nからp=min(1,(T+n/2)/B)を用い、5% warmup、85% stable、最後10% decay、最終floor1e-5 |
| 評価保存点 | B/3、2B/3、Bを越えた完了更新。実到達量/差を記録しepochと呼ばない |
| 上限到達target | targetを切らずEOTまで含める。次の完全targetを読む前に残量を確認する |
| counters | Assistant本文/EOT/bytes、応答、再露出、直列/非PAD/physical/PAD、更新、GPU秒 |

LRは更新開始前にbatchを組んで分かるTとnから決める。p<0.05では1e-4×p/0.05、0.05≤p≤0.90では1e-4、最後は1e-4×(1−0.9×(p−0.90)/0.10)とする案。最終decayのfloorは1e-5で、warmupにfloorを強制しない。両条件でこの式・開始の扱いを共通に凍結する。短いpilotだけの別scheduleでcheckpointを作り、その状態を本比較へ継ぎ足す方法は使わない。

完全targetを守るため、全更新の教師数と更新回数を完全一致させるとは主張しない。開始前のCPU dry-runで、C0/C1の更新数差5%以内、AdamWの累積乗算decay係数の相対差0.1%以内を確認する。差が大きい場合はbatch構成の設計に戻り、実行後の成績に合わせて条件を変更しない。残るbatch/長さの差は比較の限界として報告する。Teacher単位の共通化だけで完全な因果分離ができたとは扱わない。

CPUではsplit拒否、complete EOT、残budget、mask/shift、教師数平均、LR進行、評価RNG分離、保存/再開counterを確認する。CUDAでは新batchの有限BF16、連続更新と中断再開のmodel/optimizer/scheduler/RNG/sampler/実消費列の一致を確認する。新しく生じる微小なwindow跨ぎや最終短batchも対象にする。既存環境・Tokenizer benchmarkや閉鎖済み実験の反復は不要。

## 6. 評価と合格・停止条件

### 新しい未使用DEVと旧回帰を分ける

新DEVは80family（旧分類に対応する10分類×8）、うち訂正/後続/文脈から各8familyの計24を自生成履歴にも使う案とする。24会話の長さは2turn15件・3turn7件・4turn2件、計59応答として事前固定する。旧80/24/59も回帰確認に残す。新旧のfamilyを合算して独立性や成功率を水増ししない。

最終保存点のC0/C1を新DEVの主比較にする。中間保存点は発達/退行の診断として評価し、途中の最良点だけで最終成功を主張しない。候補選定に新DEVを利用したことを明記し、独立seed/最終TESTで再現するまで探索的結果とする。既存親の評価を再利用できるのはhash/suite/実装/decodingが一致した部分のみ。

| 評価項目 | 合格条件（新DEVにも同じ絶対水準を適用） |
|---|---|
| 文法と関連性 | 56/80以上がともに2 |
| 自生成最終文脈 | 15/24以上が2 |
| 固定自然停止 | 76/80以上 |
| 自生成全turn自然停止 | 57/59以上 |
| 空返答 | 固定4/80以下、自生成2/59以下 |
| role漏れ | 固定/自生成とも0 |
| Unicode破綻 | rawで0 |
| 履歴 | 固定評価の全文を保持 |
| 反復 | 既存gateの独立閾値とは呼ばず、対照より増加する候補は次段階へ推奨しない |

旧回帰と新DEVの両方でこの水準を満たすことを候補条件とする。C1–C0の内容/最終文脈のfamily単位paired差・95%CIも報告する。C1が絶対基準を満たしても対照も同じなら、教材変更による改善が証明されたとは呼ばない。両指標の差が正でCI下限も0超なら、探索的な改善信号として扱い、再現確認へ進む候補とする。複数保存点/分類のうち有利なものだけを選ばない。

第一比較では最終保存点だけを候補にする。C0/C1の両方が絶対条件を満たした場合は、新DEVの文法・関連性同時2、最終文脈2、反復の少なさの順で選び、同率ならC0とする。どちらも満たさなければ候補なし。C0だけが通った場合も共通contractで候補が成立した事実として記録し、教材C1の改善効果にはしない。旧計画128の保存点選定規則を事後に書き換える変更ではなく、この新比較の事前規則である。

固定TRAIN確認と新DEVの教師強制lossを同じ保存点で測る。C1 TRAINは7分類×16target=112、C0 TRAINは事前seedで112targetを抽出し、同じ選定済みtargetを各保存点で使う。DEVは新80の正しい提供履歴のtargetと既存RealPersonaChat DEV2,250targetを使い、C0/C1が両方を評価する。教材源ごとに本文/EOTを分離する。NLL比較は同一の対象文/bytesに限定し、違う分布のTRAIN lossの大小で品質を比較しない。提供履歴の教師強制NLLを自生成履歴での会話成立と混同しない。

合格候補がある場合に限り、元親とのBase保持（共通DEV256のBPB相対悪化5%以内、Base文法件数減なし、反復/空/role/Unicode増なし）と、128のsampling全3生成seedを確認する。保持を通ってもBase採用とは別。合格候補がなければ保持/samplingを省略し、未確認と明記する。

新DEVの全内容を理由付きで確認する。Codexによるモデル名匿名の採点も独立した人間blind評価とは呼ばない。後続の最終確認では人間blindと20%の複数採点を用意する。人間採点者が未確保なら品質完成は未確認のまま残す。誰かへ連絡したり公開で募集したりすることはこの計画に含めない。

### 小予算の途中screen

両条件のB/3到達点で固定TRAIN確認と新DEVを取得する。片方だけを途中打切りして最終C0/C1比較として扱わない。NaN/Inf、漏洩、resume不一致、数値/role/Unicodeの重大退行、時間不足なら停止する。内容の停滞だけで「10M限界」とは結論しない。最終予算まで進める価値が弱いと判断した場合は両条件を閉じて理由を報告し、途中結果でrecipeを変更しない。

## 7. 新しいGPU予算の案

**最初の教材比較一巡の累積上限を6時間とする案。** 旧runの余った枠を流用せず、将来の再開時に新ledgerへ凍結する。全stageで実時間を計上し、parent/child評価を二重加算しない。

| 区分 | 上限案 |
|---|---:|
| 変更したbatchのfinite/stable probe | 600秒 |
| 新contractのCUDA保存再開gate | 600秒 |
| C0/C1本学習 | 合計7,200秒（各3,600秒）、各B教師上限も適用 |
| Chat生成・固定TRAIN/DEV NLL・全保存点・条件付きsampling | 10,800秒 |
| 条件付きBase保持 | 2,400秒 |
| 合計 | 21,600秒（6時間） |

新DEVと旧回帰を含めた評価件数を実装後に見積もる。上限内に全必要評価が入らなければ、本比較開始前に不足を記録し計画を見直す。件数やgateを削って合格扱いにしない。予算到達時は最後の完了更新の全stateを保存し、同じ残予算でのresumeだけを認める。新seed、第二比較、効率比較、最終採用確認はこの6時間枠へ黙って追加しない。

GPU開始前は実PID/boot/start・job/lock・容量・元UIのbusy状態を確認する。記録済みPIDを現在の生存証拠にしない。中断/終端後はlock解放と元UIの復帰/状態を記録する。hardware/credential/容量等の外部blockerは理由と再開条件を保存し、同じretryを繰り返さない。

## 8. 第一比較後の分岐と後続計画

| 証拠 | 次の対策 | 追加比較の範囲 |
|---|---|---|
| 短く明確なTRAINも学べない | 教材の正解/根拠、損失、更新進行を確認。必要ならLRだけ等の1変更 | 少数の適合診断を先に計画。大規模延長なし |
| TRAIN成立、新DEV不成立 | template/条件の偏り、語彙・構造の分布差を改善 | 漏洩のない別版教材1条件。見たDEVの回答は使わない |
| 提供履歴改善、自生成で誤答を保持 | 正常履歴と誤ったAssistant履歴を対にし、Userの最新条件へ戻る回答を教える | 第二比較のC2。C1版を共通にして履歴回復例の有無だけを比較 |
| 内容改善、Base保持不合格 | 忘却/trade-offを確認し、Base replayまたはLRの一方を選ぶ | 同教師量・同混合契約の別比較。両方を同時に変更しない |
| 内容は基準内、処理効率が悪い | 同一教師列で動的paddingを比較 | 品質比較から分離。batch並びを変えるbucketingは別条件 |
| 教材変更で改善信号なし | 固定条件を閉じ、未達/限界を報告 | 自動4周目や別optimizerへ進まず、[Base復旧124](124_base_recovery_plan.md)等を別判断 |
| 内容/文脈/停止/保持で候補成立 | 独立学習seed43、人間blind、fullDEV、最終TESTの確認へ | 別の明示再開・予算。量子化/公開はさらに別段階 |

第二比較の初期案は「C1教材を共通に、同じ元親から、回復例0%対20%（教師量比）」。20%は検証済みの正しい最終回答を持つ履歴回復例で置換し、総教師量は増やさない。seed/教師budget/scheduleは共通。第一比較と一緒に実行せず、効果と失敗に応じて別計画を凍結する。旧DEVの誤生成を直接TRAINへコピーしない。新TRAINに対する学生の誤生成を使う場合も、誤答を正解として再学習しない。

効率比較では同一順序・同一更新group/教師・LRで、1024固定padding対動的paddingを測る。math/BF16の形状差で生じる数値差は既存許容値で確認し、連続/再開は同経路で全state一致を要求する。教師tokens/秒の改善10%以上を採用目安とし、品質guardは維持する。速度改善の目安を満たさない場合は元経路を保つ。複数会話の無mask packingは採用しない。

最終採用確認は別の段階で、seed43も同じ親・凍結recipeから学習する。生成seed変更を学習seedの再現と混同しない。元Base採用要件が未達なら、Chatの診断成功をBase完成へ代用しない。必要な証拠を満たしたBaseまで進める場合も通知・停止境界を維持する。新DEVを見て調整した後のprotectedTESTを、探索用に繰り返し使わない。
