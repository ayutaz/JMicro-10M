# 追加評価後のデータ・学習改善計画

ユーザーが段階1〜3の実行を指示し、2026-10-05 JSTに三条件100Mと事前条件付き全文/長文評価まで完了した。新物語はEOS/反復を改善したが親BPB悪化上限を超え未採用。以下は計画時の提案・停止境界を保持し、現在の実行範囲・凍結条件・証拠は[実行記録48](48_complete_text_10b_comparison.md)を参照する。会話の実行段階3に比較・条件付き品質判定を含めたため、本書の節4の該当評価も実施済み。節5の500M/1B/20B等は開始せず、最終report/local commitとUI復帰で停止する。

2026-10-04。ユーザー依頼は「評価をもとにここからの計画を考える。データセット量を増やしたらよいか」。今回は計画のみ。新データの取得・構築、GPU推論・学習、評価suite変更は開始しない。以下の数値は次回比較の提案で、実行config/新しい採用済みthresholdではない。[現在の実測](46_japanese_base_evaluation_v2_results.md)。

**推奨は、意味が通り、自然に完結する日本語データを増やして学習への配合を比較すること。一般Web全体を直ちに20B/50Bへ拡張する根拠はまだ弱い。** データ量が無関係とも、質だけが原因とも断定できない。データの内容・配合、学習量、最適化、モデル容量を分けて検証する。

## 判断の根拠

| 観測 | 意味と制限 |
|---|---|
| 用意したtrain12,225,819,077 tokens、現モデルの累積学習10,000,007,168 input tokens | 保存したデータ量と消費した学習量は別。10B消費は10B unique文の保証ではなく、sampler/epoch/重複を含む。データを追加しても学習へ取り込まなければ重みは変わらない |
| Web5.1B→10BでBPB0.958092→0.954018、固定反復57→53、固定EOS0→0 | 本文予測への利益はある。自由生成の停止解決は確認できない。この比較にはLR履歴差もあり、データ量だけの因果効果ではない |
| Codex一貫性2点はWeb5.1B/10Bとも0/80 | 単独の診断で独立人手ではないが、今回の目的に重要な強い反復・意味破綻を示す |
| JBLiMP sample SLOR74.62%、常識5択30.38%、意味診断の両文脈正答23.96% | 統語の選好はあるが、条件保持は弱い。意味の両文脈正答はrandom期待25%を超える証拠がない |
| 5B親で短文20%・100Mは固定EOS13/80、Web対照0/80 | 完結単位の配合への反応は実測済み。ただしraw Unicode2/400で未採用、数量・時刻・意味誤りも残る。単に同じ短文を増やせば解決すると扱わない |
| JNLI/JCoLAはlabel priorが強い | accuracyを単独の改善主指標にしない。prompt対応と理解を混同しない |

小さいモデルが、対象を絞った一貫した短い物語の学習で生成を改善できる例は[TinyStories](https://arxiv.org/abs/2305.07759)にある。英語・合成データの結果で、日本語10Mへの効果は仮説。フィルタとデータ構成を対照実験する根拠には[FineWeb](https://arxiv.org/abs/2406.17557)もあるが、日本語の特定のsourceや配合率の正解を与えるものではない。

学習tokens/parametersの比だけで「もう学習しても無駄」と判断しない。[Chinchilla](https://arxiv.org/abs/2203.15556)は計算予算に対する規模と学習量の研究で、10Mの品質上限や停止条件ではない。[反復データの研究](https://arxiv.org/abs/2305.16264)も再利用が直ちに無効とはしていない。これらを本モデルのepoch数や最適量の実測として扱わない。

## 1. 必要箇所だけ確認して、評価とデータ条件を固定する

- 既存trainのWeb/短文から固定seedで各100例だけを確認する。本文の途中切断、広告・定型句、既存反復、意味の完結、人物保持、EOS位置を確認する。sample率は全corpusの率とみなさない。EOSラベル/境界/packingを既存実装と小さい具体例で照合し、bugがあればデータ変更より先に直す。全12.23Bの再走査・重複照合は行わない。
- 基本意味診断の助数詞と日本語の自然さを直す場合は新versionへ分け、結果を見る前に固定する。現v2.1は保持する。新versionなら現10Bの変更taskだけを一度採点する。benchmarkの問題・候補・答え、評価prefixの言い換えを学習dataへ入れない。
- 文法・prefix関連性・文間一貫性・適切な内容完結を同じrubricで採点する。モデル名を隠したpacketでCodex診断を再現し、独立人手は別欄へ残す。原文法70%等の品質目標は変更しない。

## 2. 意味の通る完結文poolを小さく準備する

最初の目標は**25M〜50M tokens**の候補pool。ここで何Bも収集する必要はない。最初の比較で使うのは約20M tokensなので、一周を超えない量を先に用意する。

日常の出来事、短い説明、人物のやり取り、原因と結果が分かる文章を対象にする。2〜6文程度で一つの話題が終わり、人物・数値・時間の変化が自然なものを優先する。語彙・長さ・sourceの偏りを記録し、露骨な文章内反復や切れた末尾を除く。punctuationがあるだけで意味の完結を保証しない。文章は完全な単位で扱い、任意のtoken上限で切ってEOSを付けない。

まず既存の受け入れ済みtrainと保存sourceから必要な量だけ選別する。これは高品質subsetの整備・再配分であり、uniqueデータ総量の増加とは数えない。量や内容が足りなければ、利用条件・versionを確認できる公開日本語sourceから補う。その場合も既存trainとの重なりは分かる範囲で記録し、未確認の独立性を主張しない。大量の再dedupや有料の合成データ生成を前提にしない。

source/親文書単位でtrainと補助devを分ける。既存dev/testは保護し、新しい公開benchmarksも学習へ混ぜない。既存短文poolの長さ分布を測り、新poolで対応する長さbinを選ぶ。比較可能な約20M tokensを作れない場合は、長さの効果も変わる実験として先に仕様を改訂する。結果を見て文書長や混合率を変えない。

## 3. 現在10Bの同じ親から各100Mで三条件を比較する

| 条件 | 学習data | 分かること |
|---|---|---|
| A | 従来Web100% | 同じ追加学習量・LRによる対照 |
| B | 従来Web80%＋既存の短い完結単位20% | 以前のEOS改善が10B親にも移るか |
| C | 従来Web80%＋新しい意味の通る完結文20% | 完結文poolの変更がB/Aより生成内容に役立つか |

各100,007,936 input tokens、3,052 updates、科学合計300,023,808 tokensを提案する。B/Cの追加pool消費は各19,988,480 tokens（610 updates）。配合効果の比較であり、Cの差を意味の一貫性だけの純粋な因果効果と断定しない。source・語彙・文体も変わり得る。

共通親はfinal10B SHA `410f975d848938627aafb4fa1d5483bf45fadbb7f9c05ed7d1c8f9d45c368290`。同じmodel/Adam moments/RNG/Web cursorから明示forkする。モデル10,001,152 parameters、Tokenizer、context1024/batch32/BF16/Flash/compileは保持する。peak LR0.0002→0.00002、2,900 stable＋152 decayを既存仕上げと合わせる案。親state/LRを確認してから新config/schema/runnerを凍結する。旧5Bのrunner/configは変更・再起動しない。

新しいpool/三条件の経路に必要なtestsと短い実CUDA保存再開確認だけを行い、昔の環境・高速化・Tokenizer試験を繰り返さない。検証tokensは科学tokensと別会計。学習前にUIのactual identity/GPU lockを確認し、停止と復帰、job/log/checkpoint/source bindingを永続化する。中断は有効checkpointから再開する。

## 4. 生成内容を主に判定し、有望な枝だけ追加評価する

まず各枝でdev256 BPB、固定80 greedy64、基本意味/JBLiMP/JCommonsenseQAを測る。現在の親の保存結果は再利用する。旧v1と追加指標を混ぜず、学習量・pool量・新規source量・繰返し数を各枝で別表示する。

次回に凍結する候補選定ルール案:

- 生成一貫性2点がAより固定80中8件以上増え、prompt単位paired差の95%区間下限が0を超える。改善はCodex診断として表示し、人手品質の達成とはしない。Bとの内容差・文法/関連性・適切な完結も同時に報告する。
- 既存mixture条件（自然EOSがAより8件以上増加、元反復がA以下、dev256 BPB対照比+1%以内、空/role/raw Unicode失敗0、句読点だけの停止なし）を保持する。内容が改善しても満たさない項目を隠さず、合格へ変更しない。
- screenを通る最良候補一つと必要なA対照だけ、全文dev/固定400＋128/512の既定20 prefixを評価する。全文では既存の対照比+1%・400 raw Unicode/empty/role0等を保持する。増量候補としては別の既存条件（親の全文BPB悪化+0.001以内、固定反復増加8件未満）も満たす必要がある。
- EOS率と適切な内容完結を分ける。反復・意味診断の両文脈正答・文法/関連性の退行も記録し、新しい未測定の意味能力を達成扱いにしない。JNLI/JCoLAのlabel accuracyを単独gateにはしない。protected testは使わない。

三枝を完了し、失敗も保存して比較/report/local commitで停止する。改善しない場合に混合率やseedを次々変更するsweepへ移らない。

## 5. 結果に応じて量を増やす

| 結果 | 次の案 |
|---|---|
| Cで内容・反復・適切な停止が改善し安全条件も通る | 選んだ配合の完結文poolを100M tokens以上へ増やし、同じ配合で追加500M学習を計画。20%なら追加poolを約100M使うため、データ拡張と学習量が対応する。終了して同じ指標を再評価 |
| B/CともEOSだけ改善し意味が変わらない、または100Mでは差が出ない | 学習量不足を否定しない。人物/時間/比較/因果を含む文章を確認し、安全条件を満たすAとCを同量で延長する比較を別予算で定義する。下記の学習量比較へ |
| teacher forcingは良いが自由生成の強い反復が残る | CE対CE＋sequence unlikelihoodを各25Mの別実験として検討。新loss/rolloutの検証と別予算が必要で、今回自動開始しない |
| 三条件とも幅広く弱い | 最適化と新dataへの適合を確認し、必要なら公開日本語Baseを同じpromptで参照評価。容量不足は候補だが10Mだけから断定しない。モデル規模変更は別計画 |

成功した場合の次段階も、先に500M比較の予算・終了点を設定する。20B/50Bはその改善と実測予算が揃ってから判断する。「データセットを増やしたので学習量も無条件に増やす」とはしない。

### 学習量不足の仮説を残す（ユーザー指摘による計画補足）

2026-10-04の質問「学習量が足りない可能性はないか」への回答は**ある。現時点で収束・十分量は証明していない**。5.1B→10Bの本文BPBは改善した一方、固定生成のEOS/一貫性は改善していない。前者は学習継続の利益、後者は現区間で自由生成が改善した証拠がないという観測であり、「今後も増量は無効」という証明ではない。単一updateのtrain lossや学習率を減衰した終端lossから収束を判定しない。同一条件の中間dev系列は今回未確認で、最適化と容量の影響も残る。

100Mの比較は現10Bの約1%を追加する配合screenであり、学習量不足を棄却する実験ではない。20%配合なら対象文の学習は約20Mである。元の品質採用gateは保持するが、screen未合格を「追加学習に意味なし」と読み替えない。

- **配合×学習量を確認する別段階案:** 安全に学習できるA（Web）とC（完結文20%）を、同じ親・各枝同じLR計画で追加合計500M〜1Bまで比較する。100M/500M/必要なら1Bで同じ保護dev・生成・意味指標を測る。終端LR計画を先に固定し、中間checkpointは進捗曲線として扱う。減衰済み100M枝を場当たり的に再加熱して以前の値と純粋な量比較を主張しない。Cの100M〜200M対象文消費に対し、pool量と反復回数を明記する。Cのみ延長してAと量が異なる比較にはしない。安全停止・終了点・予算を先に凍結し、失敗でも完了報告で停止する。
- **一般Webの総学習量不足を大きい差で調べる案:** 10B対20Bも候補として残す。500M〜1Bで変化がないことは、総20Bでの効果の否定にはならない。既存stable9.5Bからstable19B＋decay1Bへ進めるなら追加10.5Bで、実測694k tokens/sの定常学習だけ約4時間12分。現在の10B結果を再利用し、同じdev/生成/意味指標、元の増量安全条件、別のGPU・保存容量予算を開始前に固定する。減衰期間差を含む学習方針全体の比較として報告し、量だけの因果効果とは断定しない。今回の4,800秒枠には含めず、50Bへ自動継続しない。

優先案は小さい三条件比較で実装・配合反応を確認し、学習量を揃えた延長比較へ進むこと。100Mでの内容改善を延長の必須条件にはしないが、安全性と独立した次段階の予算・終了条件は必要。一般Web増量と完結文増量のどちらが主因かはまだ未確定で、学習量不足を先に直接調べるなら上記20B案を選ぶ。どの案も提案で、学習再開はしていない。

## 予算と今回の終了点

実測約694k tokens/sから300Mの定常学習だけは約7.2分。新data整備、compile/save/resume、評価、内容採点は別。一次screenまでGPU上限1,800秒、条件付き全文・長文評価に追加3,000秒を提案し、合計上限4,800秒。開始前の小pilotで再見積もりし、上限時は未完了/失敗を記録する。data整備は少量sampleから処理速度を測り、全corpusの完了待ちを学習の前提にしない。

今回の完了は計画保存・status更新・local commit。実行jobなし、UIは停止しない。次の具体的作業は、再開時に限定200例のdata/境界確認と、25M〜50Mの完結文候補poolのsource/長さ/取得方法を確定すること。
