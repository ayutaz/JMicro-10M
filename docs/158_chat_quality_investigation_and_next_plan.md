# 短い日本語チャットの失敗原因と次の改善計画

2026-10-18。現行モデルは、短い文を自然に終えることに比べ、質問に答えること、人物と属性の対応、訂正の反映が弱い。**次は既存重みで原因を切り分け、その結果を根拠に教材の変更を一つ選ぶ。** 同じ追加教材の反復や学習時間の延長を先に行う根拠は得られていない。

今回の調査は、[100ケース・200応答の診断157](157_chat_quality_100_results.md)、[対照SFTの全結果156](156_answer_curriculum_results.md)、凍結した著作TRAIN全2,048件、学習・推論コード、関連する一次論文を対象とした。追加のモデル生成・GPU・学習・封印TEST読取りは0。以下の比較実験はこれから行う計画である。

## 既に説明しにくくなった原因

実API・実ブラウザーではUser入力と過去Assistant応答が送信され、全200件のprompt IDがTokenizer再計算と一致した。最大177token、文脈1024に対して履歴切断0。今回の失敗を「履歴が送られていない」「文脈長を使い切った」だけでは説明できない。[ブラウザー追試](156_answer_curriculum_results.md#後続の実ブラウザー確認同文への固定を再現)。

推論コードはリクエストごとにKV cacheを作り直し、実際のモデルlogitからgreedy生成する。返答を固定するテンプレートや回答キャッシュはこの経路にない。[生成経路](../src/jmicro/chat_evaluation.py) / [画面のEngine](../scripts/answer_curriculum_chat_demo.py)。これで全ての数値実装不具合を否定したわけではないが、先に画面だけを書き換える根拠はない。

少数TRAIN32件の暗記診断では全32件の本文とEOTを再現でき、主SFTの全更新・119 Adam state・RNG・samplerも照合済みである。「学習が一切動いていない」という説明とは整合しない。一方、Baseが未知の対話課題に必要な能力を既に持つことは、この暗記診断では確かめられない。[診断152](152_answer_learning_diagnosis_results.md)。

## 評価で追加の切り分けが必要な点

100ケースの記憶会話では、3応答目は一つの値、6応答目は二つの値を質問している。間に別属性と別話題も入る。成績低下には、距離・要求する情報数・妨害話題・自分の誤答が同時に関わり得る。**0/20を長期記憶だけの失敗と断定できない。**

また、100ケースを同じ条件で評価したのは最新C1だけである。この集合でSFTのどの変更が悪化させたかを述べるには、同じ元Baseから学習した対照C0との比較が先に必要になる。閉鎖した前回結果はそのまま残し、今回の追加診断として別runへ保存する。

参考Akebonoも、既に実行した固定20問では内容成立5/20で、属性の取り違えがあった。公開デモでチャットできることと、今回の記憶・訂正課題に安定して答えることは同一ではない。語彙数・役割形式・学習履歴も異なるため、単純なtoken上限だけで公平な原因比較にはならない。[参考の全実測](152_answer_learning_diagnosis_results.md)。10Mで不可能という結論にはしない。

## 次に進める実行順序

### 段階1 対照モデルと同じ100ケースを比べる

最新主比較のC0（checkpoint SHA先頭`55280bf3`）を、C1（`b5cb947c`）と同じCPU FP32/math・greedy・32token・同一100ケースで評価する。C0は200応答を新規生成し、C1の既存200応答は実条件が一致する記録として再利用する。各モデルの実生成履歴を戻す20会話と、提示履歴80件を分けて全件採点する。

総合成立、正しい回答値、形式完全一致、訂正、同文連続、UTF8、自然停止を同じ定義で対照表にする。全体差の区間は100caseを単位とする対応bootstrapで計算し、途中200turnを独立標本として水増ししない。既に公開した診断なので、ここでの良い結果を新DEVや採用の代わりに使わない。

### 段階2 履歴と複数情報の影響を分ける

新たに記憶10・訂正10の20familyを著作する。全familyで二つの事実を最初から与え、同じ最終質問について次の3要因を組み合わせる。

| 要因 | 条件1 | 条件2 |
|---|---|---|
| 質問位置 | 3番目のUser入力 | 6番目のUser入力 |
| 要求する情報 | 一つの属性 | 二つの属性 |
| 過去Assistant本文 | 事実と矛盾しない著作履歴 | 凍結C1が実際に生成した履歴 |

20family×8条件＝160入力をC0/C1の両方へ同じまま渡す。最終320応答を得る前に入力・正解・比較候補・判定を固定する。実Assistant履歴はC1の各family最初の5応答、計100応答を一度だけ作り、短い条件にはその2応答目までを再利用する。同じ条件のC0/C1に別々の履歴を入れて因果比較を崩さない。これは固定履歴での切り分けであり、各モデル自身の履歴で進む段階1の評価とは区別する。

短い条件は長い条件の先頭を使い、追加User発言は既存の事実を書き換えない話題に限定する。訂正は両条件とも質問前に同じ位置で完了させる。gold履歴と実履歴のtoken数差は報告し、必要な場合は長さを揃えた中立履歴を次の別比較にする。値・提示順を反転した組を含め、家族単位の差と95%CIを集計する。少数20familyで区間が広ければ、原因未確定として扱う。

同じ160入力について、事前に定めた正答と古い値・誤った対象の回答を両モデルで採点する。2候補×160×2モデル＝640個の条件付き尤度を、本文/EOT別・token数付きで保存する。最初に異なるtokenでの確率・順位も調べる。正答の確率が低い場合と、生成途中で逸れる場合を区別し、単なる平均NLL低下を正答判定へ置き換えない。

### 段階3 Baseと復号方式の寄与を補助診断する

Baseにはチャット役割を学んでいない可能性があるため、Chat形式の失敗だけで能力不足と判定しない。数値の転記、加減算、人物と属性、訂正、文字列を含む40件の短い通常文穴埋めを事前固定し、Base/C0/C1へ**同じ通常文prefix**を渡す。計120生成を比較し、同じ言い回し・範囲での能力に限定して解釈する。通常文でも失敗すればBase由来の不足を疑う材料になるが、プロンプト依存があるため事前学習全体の限界とは結論しない。

段階2で正答と誤答が競合する場合に限り、同じ重みでsamplingを補助比較する。対象20質問は結果を見る前に指定し、temperature0.7・top_p0.9・top_k0・seed41/42/43の1設定3seed、計60応答、上限32を使う。greedyの該当記録を対照にし、全seed平均と最悪値を示す。良かったseedを選ばず、反復が減っても誤答が増えれば採用しない。これはこの設定の比較であり、全sampling法の優劣ではない。

### 段階4 結果に基づいて新SFTを一つ設計する

| 診断で得た根拠 | 次に選ぶ変更 | 必要な対照 |
|---|---|---|
| 提示順や質問位置を変えると正答が落ち、適切な履歴でも弱い | 著作教材の入力構造を増やす | 既存の有限構造を使う新対照と、同じ答えを別構造で問う候補 |
| 同じUser情報でも、実Assistant履歴にすると明確に悪化する | 誤った過去Assistantに追従せず最新Userへ答える教材 | 同じUser・最終正答で、過去Assistant本文だけを変える新対照と候補 |
| 通常文の基礎課題でもBase/C0/C1が共通して弱い | その能力のTRAIN範囲を先に調査し、別の能力学習案を設計する | Baseの問題をSFTだけの問題と決めず、同10M内で独立提案する |
| samplingだけで精度を保った反復改善が出る | 推論方式だけの別比較 | 重み・入力・上限を固定したgreedy対照 |
| 差が不明瞭、または複数の説明が残る | 不足している比較を一つ追加する | 根拠のない学習やハイパーパラメータ探索へ移らない |

SFT候補の第一案は**同じ正答を維持したまま入力の配置を変える比較**とする。元の2,048対象と教師本文IDを保ち、提示順・訂正位置・途中話題・質問文を変える。どの変更を使うかは診断の根拠で一つの生成方針に絞る。英数字・減算・二情報の答えなど新しい正答をまとめて追加する案とは分ける。

対照・候補は元10B Base/fresh Adam、native10,001,152、LR1e-4、seed42、同schedule/更新512教師/最大32×1024/BF16/mathを共通にする。共通の既存教材とsource配合、正答token列・消費順・alias・教師マスク・約1M教師の終端を揃える。入力変更だけなら出力教師tokenは同じなので、CPU全消費で教師量と更新境界を厳密照合できる。新対照は旧重みの続きではなく新規学習とし、旧C0/C1は歴史対照として残す。

構造変更で履歴が長くなった分は入力token・wall・peak memoryも別記する。入力量や計算費用まで同一という主張はしない。答えを変える新教材が必要なら、この設計を流用せず別の配合・対照・終端を事前に定める。

候補作成にはTRAINだけを使い、今回の100case・段階2の20family・既存DEVを正解教材や誤答収集元へ転用しない。実モデル誤答を教材へ使う場合もTRAIN専用入力で取得し、教師は検証した事実から作る。モデルの誤答をそのまま正解にしない。

### 段階5 新DEVと実会話で採否を決める

TRAINを確定してから、新DEV80件と24実会話を作り、条件・source・checkpoint・採点をfreezeする。値置換だけの重複を避け、構造・訂正対象・提示順・単一/複数属性を分ける。旧6suiteも残す。7suite×219応答×2腕＝3,066応答、追加で公開100case×200応答相当の両腕400応答を回帰確認する。全3,466応答を理由付きで確認し、同一raw判定の再利用は従来の厳密一致条件を満たす場合だけにする。

既存の採用条件を維持する。新DEV内容成立56/80以上、実履歴24会話の最終文脈成立15/24以上、provided自然停止76/80・own57/59以上、空provided4/80・own2/59以下、role漏れ・UTF8破損・履歴切断0、反復の増加なし。新DEV内容差の対応family bootstrap 95%CI下限>0と、旧6suiteの内容・文脈・停止・空・反復の件数悪化なしも満たすこと。総合成立と回答値は追加報告し、旧指標の代わりにしない。細かい集計キーを起動前configに列挙する。

不合格ならその固定条件を閉鎖する。途中checkpointや良い評価組への差替えで救済しない。有望な場合のみ別契約でSFT seed43再現と追加実ブラウザー会話へ進む。この再現は親Baseの事前学習からの独立全pipelineや封印TESTではない。正式Base認定・独立全pipeline・全文DEV・標準440・新封印TESTの残課題は別途保全する。
