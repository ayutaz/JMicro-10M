# 生成の逸脱・停止位置・教材適合性を切り分ける次の計画

2026-10-05 JST。[結果79](79_narrative_diversity_results.md)を踏まえた提案。ユーザーの「ここからの計画を教えて」に対応する。今回完了した三段階の後の新しい診断・学習は開始しない。元10B UIと全checkpointを保持する。

基本意味は58.333→64.583%に改善したが、EOS30→7、一貫性6→3、適切完結6→2（各80）。正解本文でのEOS尤度と自由生成停止が異なり、source・長さ・EOS密度も変化した。次は、学習量だけ、容量だけと結論せず、どこから出力が崩れるかを確認してから変更を選ぶ。

## 1. 保存済みモデルだけで、正解文と自由生成の差を診断する

**目的**: 新教材が学習されていないのか、学習しても自由生成で逸脱するのか、64tokensという出力上限が停止を妨げるのかを分ける。

新poolの既に固定したsampleからtrain32と、公式devから別の32全文を固定する。devは学習へ混ぜない。同量100Mの対照・候補の二checkpointで、同じ第一文から正解の続きに対する本文NLL・次token順位・文末EOS確率/順位と、無制約greedy64/256を比較する。prefixは元token列に結び付け、tokenization境界の差を確認する。全生成と反復開始位置、対象・時系列・否定・主体が変わる最初の箇所を保存する。正解のEOS位置まで進めた時と、逸脱した文脈でのEOS確率を区別する。

256tokens生成は長さを切り分ける追加診断で、既存greedy64品質gateの合格へ置き換えない。正解続きを見せた評価を自由生成能力とは扱わない。EOS教師NLL改善だけで停止問題が解決したとも判断しない。

**ゴール**: 各モデルの全64入力についてgold条件と両出力上限の結果・原文理由をそろえ、未学習、生成中の逸脱、上限による切断、EOS低順位を分類して次の変更を一つ選ぶ。新科学学習0、GPU占有上限案600秒。旧全suite・全corpus照合を再実行しない。

## 2. 診断に応じて、一つの条件だけを同量で比較する

以下を全部同時に実行する計画ではない。段階1の証拠で一案に絞り、設定・原文・予算を実行前に別契約へ固定する。

- **EOSの順位が主問題なら**、同じ新pool、出発10B、Web/short教師量、shuffleとLRを保ち、EOS loss係数1と約2.31を比較する案。2.31は今回の短文EOS教師386033/167151に基づく候補値で、最適値ではない。教師tokensは各100M（Web80M/short20M）で同じにし、重み付けしたlossと実教師数を別記する。新wrapperだけで実装し、末尾EOSのlossと実CUDA保存再開を確認する。早すぎる停止や意味のない完結も失敗として保存する。
- **長さ・作風が主問題なら**、40〜80body tokens程度で自足する日常の全文へ絞り、対照と文書数・長さ分布・EOS密度をそろえた教材比較を行う案。原文を途中で切らず、氏名だけの増量を避け、既存sourceから得られる固有量を正直に記録する。1万件や1Mという量を先に強制せず、1000件程度の良質な一致poolで準備を終える。dev/testを教材選択へ流用しない。
- **gold条件でも学習例の続きを予測できないなら**、増量前に、その実入力のlabel/mask/attentionとloss、勾配、optimizer更新を追跡する。結果72の未解決数値7失敗も実際に影響する経路だけで再確認し、修正対象を特定する。記憶成功や数値誤差だけから容量限界を決めない。

**ゴール**: 選んだ一条件について各100M以下の同量比較と共通日本語評価・固定160生成の全内容を完了する。GPU占有上限案1200秒。基準は一貫性の対応+8/80・95%下限>0、一貫性/適切完結各27以上、EOS37以上、反復18以下、raw empty/role/UTF8なし、既存BPB条件を維持する。単に句点やEOSが増えることを採用条件にしない。

## 3. 改善を確認した条件を拡大するか、モデル設計の比較へ移る

**目的**: 根拠のある改善を伸ばし、改善しない条件への長期学習を避ける。

全品質基準を通れば、良い原文の固有量を増やせることを確認し、追加500M程度の教師学習を別契約で固定する。データセット量と反復を含む学習量を別々に記録し、同じ評価で改善と劣化を確認する。

良質な短文を正解条件では学習できても、対照と比べ一般生成が改善しない場合は、モデル設計・表現能力を次の比較対象にする。10Mという目標を保つ構成比較を先に設計し、異なる構成を同じ初期化条件・corpus・学習量で比較する。10B済みモデル対未学習モデルの比較で容量を判断しない。Tokenizerを比較する場合は共通bytesのBPBとbytes/GPU時間もそろえる。具体的な構成は調査・予算固定後に選び、今回は変更しない。

**ゴール**: 採用・非採用と残る原因を決め、結果・local commit・元UI復帰後に停止する。いずれの分岐でも「データを増やせば解決する」「10Mでは不可能」という結論を先に置かない。uv Python3.12.7、WSL/RTX4090を維持し、保護test、Chat、20B/50B、push、公開をこの提案に含めない。
