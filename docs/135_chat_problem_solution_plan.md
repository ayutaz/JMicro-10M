# Chatの課題を解決する方法と検証計画

作成: 2026-10-13 JST。今回の「これらの問題に対する課題の解決方法とその計画を立ててください」への回答。**今回は計画と記録の更新のみ。学習、GPU診断、新しい教材・DEVの作成は開始しない。** 以前の実行記録・準備済みファイルを調べた事実と、これから行う提案を分ける。10,001,152 parameters、約10Mの上限、元Tokenizer、日本語Baseの目標、元の品質基準を維持する。

結論は、教材の汎化を検証する同条件比較を第一に置くこと。既存BaseからChatへのSFTという方向は診断として妥当だが、既存の雑談教材を追加学習するだけでは内容品質の解決を確認できていない。Chatの診断結果をBase完成の証拠にも読み替えない。

## 何が分かっていて、何が未確定か

[調査130](130_chat_failure_improvement_investigation.md)、[比較結果132](132_chat_improvement_execution.md)、[次比較案133](133_chat_generalization_followup_plan.md)を根拠にする。直近の完了比較は次のとおり。

| 指標 | 雑談教材C0 | 条件回答教材C1 | 必要な条件 |
|---|---:|---:|---:|
| 新DEVの文法・関連性がともに2 | 11/80 | 15/80 | 56/80以上 |
| 新DEVの自己生成履歴・最終文脈2 | 4/24 | 2/24 | 15/24以上 |
| 固定応答の自然停止 | 70/80 | 77/80 | 76/80以上 |
| 自己生成会話の自然停止 | 45/59 | 59/59 | 57/59以上 |

C1は停止と文法を改善したが、文法2の62件中47件は関連性2未満だった。最終C1の固定TRAIN本文NLLは約0.000006、同じ点の新DEV本文NLLは3.883688。教材の暗記・分布のずれを疑う強い観察だが、原因を一つに確定する証拠ではない。固定TRAIN112targetの結果を全TRAINへ一般化しない。C1−C0の正答率差は+5ポイント、95%CIは−5〜+15ポイントで、内容全般の改善は確定していない。

Assistant本文+EOTの教師mask、単一shift、実教師数によるCE平均、短い評価での履歴削除0は確認済み。これらを理由なく作り直す優先度は低い。GPU・保存再開の成立と、モデルの回答品質は別である。Base不足、LRの不適切さ、10Mの容量限界は未確定。

## 問題ごとの解決方法

| 課題 | 解決方法の提案 | 改善を確認する方法・残る限界 |
|---|---|---|
| 読めるが質問に答えない | 人物・場所・時刻・数量・選択など、要求された情報を先に答える教師を用意する。明確な質問には答え、不足情報があるときだけ聞き返す | 未使用の自然文で内容を採点。正解単語の一致だけで合格にしない |
| TRAINを覚えるがDEVへ移らない | 名前紹介やgoldの前置きに依存しない最初の質問を学習する。独立した会話構造、自然な表現、複数の回答形式を増やす | TRAIN/DEV本文NLLと自由生成を併記。人物名の置換や同じテンプレートの大量生成を独立した教材増加に数えない |
| 訂正・否定・複数条件を守れない | 古い値→最新値、許可→禁止、対象A→対象Bで答えが変わる対を作る。必要な履歴条件と正解根拠を確認する | 古い値の採用、否定対象の選択、未提示値の創作、条件の混合を分類。正しい提供履歴で先に検証する |
| UserとAssistantの事実を混同する | Userの属性・引用された話者・Assistantの提案・確定事実を区別する。AI自身の架空の体験を教師にしない | 誰の予定・所有・経験かを内容確認。役割tokenが漏れないことだけでは意味上の話者区別を認証しない |
| 自分の誤答を次turnへ持ち越す | 正しい履歴での改善後、TRAINだけに検証済みの誤ったAssistant履歴を加え、Userの最新条件へ戻る正答を教える | 正しい履歴、制御した誤履歴、実際の自己生成履歴を同じfamilyで比較。誤答そのものを正解として学習しない |
| paddingが多く遅い | 品質比較から分離して動的paddingを検証する。教師順・更新group・位置・mask・LRを保つ | 教師列とcounter、損失/勾配の事前許容差、連続/再開を確認した後に時間・VRAMを測る。PAD率から速度向上率を推定しない |
| 評価者と教材作者が重なっている | TRAIN固定後に新しいDEVを作り、旧DEVは回帰確認として残す。最終候補には独立学習seed43・人間blind評価を追加する | family単位のpaired比較とCI。保存点・同一会話のturnを独立標本として水増ししない。protectedTESTは選定終了まで使わない |

## 既にある準備と、まだない証拠

[実行準備134](134_chat_generalization_execution.md)のWSL小記録を読み取った。準備済みD1は40,126 target、1周660,065 Assistant本文+EOT教師、最初の単一Userへのtargetが23,515件（約58.6%）。固定280sampleはCodex非blindで問題0という記録で、260件は完全に同じ内容の以前の判断を参照し、変更20件を再確認している。独立人間の確認、全TRAINの意味的正しさの認証ではない。

教師消費のCPU dry-runにも合格記録がある。ただしこれはGPU学習・モデル品質の証拠ではない。D1は既存の意味familyを中心とした改訂で、独立した自然会話の幅が十分になったとは言えない。新DEVの `dev.jsonl` と `dev_authored.json` は今回の確認では存在しなかった。新しい凍結実行config、CUDA gate、実学習、D1の回答品質は未確認として扱う。

今回の観察と元記録hashは[計画の確認記録](../reports/investigation/chat_solution_plan_20261013/observations.json)に保存する。準備済みTRAINは上書きしない。内容・多様性の見直しで改訂が必要なら、元版を残して別版として凍結し、対応する新DEVも学習前に固定する。

## 実行を再開する場合の順序

| 段階 | 行うこと | 次へ進む条件・成果物 |
|---|---|---|
| 0. 比較の事前登録 | D0=前回C1教材、D1=改訂教材として、変更点・親・seed・予算・保存点・採否を固定する。準備済み教材の根拠と多様性の不足を点検する | 設計書とhash一覧。教材全体のrecipe比較であり、first-turn等の個別因果効果とは主張しない |
| 1. 教材と評価の固定 | TRAINの正解根拠、自然さ、話者、助数詞、first-turn比率、応答長、EOT比率、family偏りを確認する。TRAIN実体の凍結後に未知familyの新DEV80を作り、24会話・59turnの自己生成評価も固定する | 内容確認の理由、split・重複検査、機械検査と人間確認の区別。旧DEVの具体例・失敗出力をTRAINへコピーしない |
| 2. 実装・資源のgate | 新しい入口とconfigを完成し、変更経路の有限BF16、教師消費、保存再開、評価時間を確認する。旧実験の証拠は条件一致を監査して再利用する | 本学習前の技術gate合格と、全評価・保存まで予算内に収まる見積もり。上限内に収まらなければ開始せず報告 |
| 3. 同条件の学習比較 | 同じ元WebUI10B親からfresh optimizerで学習する。D1を学習済みC1から開始しない。B/3・2B/3・Bで保存する | 全state checkpoint、実教師・EOT・bytes・非PAD/physical入力・更新数・GPU時間の記録。probeの重みを本学習へ混入させない |
| 4. 全評価と採否 | 親と各保存点で新旧の固定80、無抑制80、自己生成59turn、共通targetのTRAIN/DEV本文・EOT NLLを確認する。全rawと理由付き内容判断を保存する | 最終Bの新旧両suiteで下記screenを判定。中間点の良い値を後から採用点にしない。paired CIと全失敗を報告して一度止める |
| 5. 条件付きの後続 | 内容screenを満たす候補だけ、事前登録済みBase保持・samplingを確認する。正しい履歴での基準到達後に限り誤履歴回復比較を提案する | 保持未確認を保持合格にしない。回復比較、padding比較はそれぞれ別条件・別予算として登録する |
| 6. 最終確認 | 有望recipeに独立学習seed43、人間blind、fullDEV、最終継続suite、選定封印後のprotectedTESTを行う | 元のBase/Chatの完成条件を満たして初めて採用候補。量子化・配布は別段階 |

最初の比較では各条件 **B=1,899,555 Assistant本文+EOT教師tokens**、seed42、native10M、Tokenizer、教師量基準scheduleを共通にする。完全応答単位の終端超過0〜64、長さ分布・EOT比・更新数・累積decayの許容差は実行前に固定し、実消費でも監査する。同じ教師量は同じGPU費用を意味しない。

D0は旧C1と同じrecipeなので、親・TRAIN・実装・seed・schedule・sampler・全stateの一致を証明できる場合は保存済みcheckpointを対照として再利用できる。新DEVの評価は必要で、過去checkpointを新しい学習seedの証拠には数えない。一致が証明できない場合は再利用を成立扱いせず、比較設計を学習前に修正する。完了した旧job自体を再起動しない。

第一比較のGPU上限案は**累積6時間**。参考として前回はprobe・再開・2条件の学習・評価を含め約70.8分だったが、新教材での時間保証ではない。内容レビュー、CPU監査、人間確認の時間は別。後続の誤履歴回復・効率比較・最終確認をこの枠へ自動追加しない。GPU秒の内訳と残りの全評価時間を実測して凍結し、上限超過や評価省略で続行しない。

最終screenは、新旧両方で文法・関連性同時2が56/80以上、自己生成最終文脈2が15/24以上、固定自然停止76/80以上、自己生成自然停止57/59以上。元の空応答上限4/2、役割漏れ・raw Unicode破損・履歴削除0、D0比の反復非増加も維持する。これは比較のscreenであって、Base/Chatの最終採用条件を代替しない。

## 結果による分岐

| 観察 | 次に検討すること |
|---|---|
| TRAINはほぼ暗記できるが未知DEVが改善しない | 教材の構造・意味的多様性・分布のずれを再設計する。名前や数値の置換数、学習周回だけを増やさない |
| 検証済みの短いTRAINにも適合しない | 技術gateと教師量を確認した上で、教材を固定したLR等の変更を最大1つに絞る。Base不足・容量不足を即断しない |
| 正しい履歴なら基準に届くが自己生成で落ちる | 誤履歴からの回復教材を別の同予算比較で検証する。モデル誤答を教師へそのまま採用しない |
| Chatが改善してもBase保持が落ちる | 採用せず、保持を主目的とする混合・学習強度の別比較を提案する |
| 一巡しても内容品質が未達 | 条件を閉じ、残る仮説と失敗を報告する。必要なら[Base復旧124](124_base_recovery_plan.md)で次の比較を1件に絞る。自動延長・基準緩和・大型化をしない |

## 公開研究・参考モデルの扱い

[TinyStories論文](https://arxiv.org/abs/2305.07759v2)は制御された英語物語教材で10M未満の生成を報告している。教材を重視する根拠にはなるが、日本語汎用Chatの成功を保証しない。[GKD論文](https://arxiv.org/abs/2306.13649v3)は教師系列と自己生成系列の分布のずれを扱う。誤履歴回復を切り分ける参考であり、本計画の通常SFTをGKDの実施済み結果とは呼ばない。

Akebonoについては[固定資料と調査127](127_rebuild_investigation.md)も参照する。今回、通常のWeb取得ではHugging Faceページが取得不可だったが、[rawモデルカード](https://huggingface.co/hisakata-ai/akebono-10m-chat/raw/main/README.md)は取得できた。カードは通常会話成立3/40、長会話0/12、END終了168/168と記述している。配布者の既存報告で、独立再測定ではない。終了できることと会話内容が正しいことを分ける必要があり、構成を移植するだけで解決recipeとは判断しない。カードには公開前という文言も残っているため、現在の配布状態をその文言だけで断定しない。指定GitHubページのWeb取得は404だったが、ローカルの実装と保存結果は今回の調査に利用できた。

計画作成の完了と、改善の実証・モデル完成は別である。今回の依頼では新しい実験・教材生成・GPU利用、push・公開を行わない。
